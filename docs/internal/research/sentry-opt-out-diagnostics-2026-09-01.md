# Sentry opt-out error diagnostics

Date: 2026-09-01

## Decision

EVB Viewer can technically send default-on Sentry error events, but one policy does not fit all three runtimes.

- **Nitro server errors:** default-on with an opt-out is supportable under GDPR legitimate interests after EVB completes the work listed below. This is the fastest low-risk source of useful diagnostics.
- **Electron and hosted-browser errors in the EEA:** keep opt-in. Even a sanitized stack or error code is information read from terminal equipment and sent by EVB-controlled software. Article 5(3) of the ePrivacy Directive normally requires consent unless a narrow transmission or strictly-necessary exemption applies. No primary source reviewed establishes a general exemption for product error reporting.
- **Microsoft Store Electron build:** keep opt-in. Microsoft Store Policy 10.5.2 requires in-product opt-in before a product publishes customer Personal Information to an outside service.

The proposed Cursor-style unchecked `I don't want...` box is therefore unsuitable. If consent is required, silence or an unchecked refusal box is not affirmative consent. If EVB relies on legitimate interests for Nitro, the control is an objection mechanism, not consent. Use a checked positive toggle such as `Send privacy-sanitized error diagnostics`, explain the processing beside it, and honor an off choice immediately. Do not mention training in this control because EVB has no training purpose. [EDPB Guidelines 05/2020 on consent](https://www.edpb.europa.eu/our-work-tools/our-documents/guidelines/guidelines-052020-consent-under-regulation-2016679_en), [CJEU Planet49 judgment](https://eur-lex.europa.eu/legal-content/EN/TXT/?uri=CELEX:62017CJ0673)

## Exact diagnostic scope

The broader requirement is workable without weakening the strict event contract in [the error telemetry ledger](../sentry-error-telemetry-ledger-2026-09-01.md): every UI-displayed error and every red `console.error` enters an EVB-owned diagnostic seam, but only a newly constructed, allowlisted error record may leave the runtime.

For a UI error, the presentation seam should report a closed `DiagnosticCode`, operation, severity, runtime, release, and bounded scalar context. It must not scrape or send the localized UI message. The UI may contain a filename, document text, parser message, or another value prohibited by the ledger.

For `console.error`, an EVB wrapper may observe the call, but it must ignore every console argument. Raw arguments can contain arbitrary objects, document content, URLs, local paths, exception messages, credentials, or user text. The wrapper should create a fresh call-site stack, remove wrapper frames, retain only application-owned canonical frames, and emit a static code such as `UNCLASSIFIED_CONSOLE_ERROR`, or a more specific code supplied by the call site. Calls with no application-owned frame should be dropped. Do not use Sentry's console-capture integration, `captureException` on a console argument, argument stringification, or console breadcrumbs. Sentry documents that its JavaScript SDK otherwise sends console messages as breadcrumbs and that those messages may contain PII. It also documents default collection of request headers, URLs, query strings, context lines, and Electron native minidumps, which is why the ledger's `defaultIntegrations: false` and final event reconstruction remain necessary. [Sentry Electron data collection](https://docs.sentry.io/platforms/javascript/guides/electron/data-management/data-collected/), [Sentry Electron options](https://docs.sentry.io/platforms/javascript/guides/electron/configuration/options/)

"Every error" should mean every occurrence reaches the local sanitizer. It should not mean that every duplicate becomes a separate network event. One logical failure may appear in both the console and UI, and a loop can emit thousands of identical errors. Use process-local provenance and burst suppression so Sentry receives one structured event plus the ledger's bounded `suppressedCount`. This keeps selected errors at 100 percent coverage while meeting GDPR necessity and minimization.

The scope remains error events only. It excludes analytics, replay, tracing, profiles, Sentry Logs, breadcrumbs, sessions, documents and user content, attachments, minidumps, request or response data, and raw local logs.

## GDPR basis and notice work

GDPR does not make consent the only lawful basis for diagnostics. Article 6(1)(f) permits processing necessary for a controller's legitimate interests unless the person's interests or rights override them. Before enabling Nitro capture, EVB must write and approve a legitimate-interests assessment that:

1. states the current, specific interest, namely finding and fixing EVB Viewer operational errors;
2. proves necessity, including why local-only reports or a less intrusive method would not achieve the same result; and
3. balances the small structured record, likely user expectations, affected users including children, safeguards, retention, and consequences.

The EDPB says these three conditions are cumulative, the balancing test must happen before processing, and legitimate interests are not a default fallback. Its 2024 legitimate-interest guidelines are an adopted public-consultation version, so the GDPR text and decided cases remain controlling. [GDPR Articles 5 and 6](https://eur-lex.europa.eu/legal-content/EN/TXT/?uri=CELEX:32016R0679), [EDPB Guidelines 1/2024](https://www.edpb.europa.eu/system/files/2024-10/edpb_guidelines_202401_legitimateinterest_en.pdf)

The first-layer notice must name EVB as controller, say that sanitized error records go to Sentry for error diagnosis, identify legitimate interests where used, list the record fields and excluded data, identify Sentry and relevant subprocessors, state the EU storage region and any transfers, give the retention period, and explain access, deletion, restriction, and objection. Article 21 requires EVB to call out the right to object clearly and separately at the first communication and provide an online method. EVB should honor the diagnostics toggle unconditionally rather than attempt to prove overriding grounds. [GDPR Articles 13 and 21](https://eur-lex.europa.eu/eli/reg/2016/679/oj/eng/), [Irish DPC transparency guidance](https://www.dataprotection.ie/en/organisations/know-your-obligations/transparency), [Irish DPC right-to-object guidance](https://www.dataprotection.ie/en/individuals/know-your-rights/right-object-processing-personal-data-article-21-gdpr)

EVB should execute Sentry's DPA, keep the project in Sentry's EU region, disclose Sentry's 90-day Business-plan error retention, delete resolved issues during weekly triage, disable IP storage, enable server-side scrubbing as a backstop, and keep native crash-report storage at zero. The original research recommendation to require Sentry MFA is superseded by the recorded owner decision in the architecture and account-control ledgers: routine login uses the connected Google account, personal Gmail cannot configure organization SSO, Sentry exposes no password-removal control, and Sentry-native and organization 2FA remain off for this route. Sentry's DPA identifies EVB as controller and Sentry as processor, limits Sentry to documented lawful instructions, and prohibits sensitive data. Scrubbing is a fallback, not permission to send raw payloads. [Sentry data retention periods](https://docs.sentry.io/security-legal-pii/security/data-retention-periods/), [Sentry DPA](https://sentry.io/legal/dpa/), [Sentry security controls](https://sentry.io/security/), [Sentry organization privacy settings](https://docs.sentry.io/api/organizations/update-an-organization/), [Sentry EU data region](https://sentry.io/changelog/data-storage-location-in-germany-is-generally-available/)

## Why client opt-out is not the low-risk EEA choice

Article 5(3) of the ePrivacy Directive covers storing information or gaining access to information already stored on a user's terminal. It allows this without consent only when the operation solely carries a communication or is strictly necessary to provide an information-society service explicitly requested by the user. [ePrivacy Directive Article 5(3)](https://eur-lex.europa.eu/legal-content/EN/TXT/PDF/?uri=CELEX:02002L0058-20091219)

The EDPB's final Guidelines 2/2023 make the technical scope broad. "Information" includes non-personal data; laptops are terminal equipment; JavaScript, distributed software, and SDK instructions that make a device send information can constitute access; and stored information includes RAM, CPU cache, and results created by programs. A sanitized stack, code, runtime, or derivation can therefore remain in scope. Sending through a first-party Nitro proxy instead of directly to Sentry does not remove the access operation. The EDPB leaves exemptions to case-by-case analysis under each member state's transposition and regulator guidance. [EDPB Guidelines 2/2023, version 2.0](https://www.edpb.europa.eu/system/files/documents/2024-10/edpb_guidelines_202302_technical_scope_art_53_eprivacydirective_v2_en_0.pdf)

EVB's PDF-viewing service still works when remote diagnostics are off, so calling product-improvement error reporting "strictly necessary" is a weak global position. The Irish DPC describes only the transmission and strictly-necessary exemptions. CNIL's 2025 mobile-app recommendation, which invites adaptation to Windows, macOS, and Linux, recommends consent for OS crash-report systems and minimization. This is regulator guidance, not a ruling on EVB's structured error events, but it weighs against assuming a broad diagnostics exemption. [Irish DPC terminal-tracking guidance](https://www.dataprotection.ie/en/faqs/cookies/my-website-or-app-uses-cookies-and-other-tracking-do-i-have-get-consent-users), [CNIL mobile-app recommendation](https://www.cnil.fr/sites/default/files/2025-05/recommendation-mobiles-app.pdf)

If a future jurisdiction-by-jurisdiction review establishes an exemption for this exact client record, GDPR legitimate interests could govern the later processing and an opt-out could replace consent there. Until then, do not ship a default-on EEA client based only on GDPR Article 6(1)(f).

## Runtime and store result

| Runtime | Technically possible | Policy to ship |
| --- | --- | --- |
| Electron direct distribution | Initialize the main-process adapter unless a persisted setting is off. Renderer still sends only typed records to main. | Opt-in for the EEA. An opt-out build is possible only for a separately reviewed jurisdiction where terminal-equipment consent is not required. Geography inferred from IP, locale, or download location is not reliable enough to silently switch the legal model. |
| Electron through Microsoft Store | Same implementation, with a store-build policy flag. | Opt-in. Microsoft defines Personal Information broadly and requires express in-product permission before publishing it to an outside service, plus disclosure and later rescission. A network source IP and linkable diagnostic record make it unsafe to assume the rule does not apply. [Microsoft Store Policies 10.5.1 and 10.5.2](https://learn.microsoft.com/en-us/windows/apps/publish/store-policies#105-personal-information) |
| Hosted browser client | A deferred browser adapter can send the same structured record directly or through Nitro. | Opt-in for the EEA. A same-origin proxy does not avoid Article 5(3). Ask just after the first error, before transmitting it, when the reason for the request is concrete. |
| Nitro server | Capture an EVB-owned server record without instructing client code to read or send device information. | Default-on under legitimate interests after the assessment and notice work. Remove request data, route parameters, URL and query, headers, cookies, body, user IP and identity. Treat the remaining record as potentially linkable through timestamp or deployment logs until EVB proves otherwise. |

The repository currently packages Microsoft Store AppX artifacts, so Microsoft's rule applies. Its macOS targets are direct `dmg` and `zip`, not Mac App Store `mas`, so Apple's App Store rules do not currently govern those builds. If EVB later adds Mac App Store distribution, Apple requires an in-app and store privacy policy, accurate third-party disclosures, and App Privacy declarations for `Crash Data` or `Other Diagnostic Data`. Apple permits reliance on GDPR legitimate interests only when every condition of that law is met; this does not displace ePrivacy. [Apple App Review Guideline 5.1.1](https://developer.apple.com/app-store/review/guidelines/#privacy), [Apple App Privacy data types](https://developer.apple.com/app-store/app-privacy-details/), [Apple third-party disclosure instructions](https://developer.apple.com/help/app-store-connect/manage-app-information/manage-app-privacy/)

## Lowest-risk useful rollout

1. Enable default-on **Nitro-only** structured error events after the legitimate-interests assessment, layered notice, Sentry DPA, EU-region, retention, access, and privacy-setting gates pass.
2. Keep Electron and browser diagnostics off until affirmative opt-in. After the first UI-visible error, show a non-blocking explanation and an unchecked positive control, `Send privacy-sanitized error diagnostics`. Send that occurrence only if the user opts in. Keep the same control in Settings and link the complete notice.
3. Route every UI error and `console.error` through the local seam immediately, even before consent, but discard the sanitized record locally when client reporting is disabled. Never buffer it for later upload.
4. Keep Nitro objection separate from client consent. A checked positive Nitro control may be default-on where legitimate interests applies. Persist only the preference needed to honor the choice, and do not attach a stable diagnostic identifier.
5. Disable Sentry AI features and do not enable Seer. Do not seek permission for training because training is outside EVB's purpose. Sentry states that it does not train generative AI models on customer data by default without permission; the stronger operational guarantee is EVB's disabled AI setting plus the DPA's processor-purpose limit. [Sentry Seer privacy statement](https://docs.sentry.io/product/ai-in-sentry/seer), [Sentry DPA](https://sentry.io/legal/dpa/)

This hybrid starts producing server-side evidence quickly, asks client users at the moment diagnostics are relevant, and preserves the ledger's closed event contract. A global default-on Electron/browser switch should remain blocked until EVB has a documented Article 5(3) exemption analysis for each EEA jurisdiction it intends to cover and a separate Microsoft Store-compliant opt-in path.
